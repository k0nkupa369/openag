# Agent requests

## Independent messages

`agent_send` records a bounded request to an existing agent and returns admission immediately. `agent_consult` is a compatible name for the same operation. The sender finishes its turn and dispatch without waiting for the recipient. Each recipient returns its own attributed reply; the daemon delivers that reply in a separate sender turn when the sender is available. There is no batch join or mandatory wait for other replies. An explicit acknowledgement does not automatically require a return reply. `agent_request_cancel` cancels one or all requests made by this agent in this conversation.

Discovery returns durable agent IDs, editable current handles, names, redacted role descriptions (up to 200 characters), runtime availability and busy state. It does not expose private instructions or configuration. Current/retired handles with or without @ resolve to the same agent. Display names can repeat. `replyToRequestId` correlates an explicit follow-up and must name the same requesting agent, recipient and origin conversation. It does not share old private context automatically. Legacy output-parsed room delegation remains available; explicit messaging suppresses duplicate prose delegation in the originating turn.

## Coordinator judgment

The default bot in its direct chat and the room lead in a room coordinate the owner's request. They choose a specialist whose role clearly fits a separable part: use `agent_consult` for bounded questions or reviews, and propose assigned Work through `create_work` for an ongoing handoff, subject to the ordinary review and start rules. Room leads choose members; the default bot uses `agent_list` before routing and may assign Work to a guest specialist. The coordinator handles quick answers, tightly dependent steps and same-thread follow-ups itself, follows an explicit agent choice or request to do it personally, and handles the task itself when no role fits unless the owner asks it to create a specialist. If missing descriptions make a choice unclear, it says so briefly.

The coordinator checks availability before choosing a recipient. If that agent is busy or unavailable it tells the owner and offers to do the work itself, without silently retrying. This is guidance: the underlying request mechanism can queue a busy recipient, as described below. A consultation includes the goal, constraints, relevant excerpts and expected return because the recipient has no other conversation context or attachments. Admission is not completion; the coordinator uses attributed findings when they arrive.

Questions have an 8,000-character limit; explicit selected context has a 16,000-character limit. Both are redacted. Specialist findings are capped at 16,000 characters with an explicit shortening marker. The existing runtime projection records additional omissions. These are JavaScript string-length limits, not token estimates. Requests have no fixed overall deadline for dispatch, execution or synthesis. A service restart interrupts requests without replaying them. Individual model and tool operations can still have their own limits. Pausing the initiating turn for input cancels its admitted consultations instead of leaving the recipient reserved.

A busy recipient accepts a queued request without interruption. Dispatch waits for active turns, pending approvals/receipts, configuration and active Work to release it. The queue wakes on runner completion, configuration completion and relevant Work/approval/receipt changes; it does not poll a model. Per-origin and per-recipient outstanding requests are bounded at 50; one message admits at most three requests. Source validation and guest preflight check capacity before the user message is stored.

## Context and authority

A request includes an 8,000-character question and up to 16,000 characters of explicitly selected context. Both are redacted. Include objective, decisions, constraints, evidence and expected result. Specialist findings retain the latest output up to 16,000 characters, with a marker when earlier progress was omitted. These are JavaScript string lengths, not tokens.

Specialists run in private request contexts through the normal runner and central tool gate. They keep their identity, operating instructions and assigned skills, but receive no automatic source transcript, recipient DM history, memory head or vector recall. Requests are not vector-indexed. Direct-chat guest mentions forward only the submitted message and its explicitly bound attachments/quoted reply. Guest answers remain attributed in the original chat without membership changes. Named rooms and other ingress retain member-only addressing. Explicit text consultations do not forward attachments automatically.

Only eligible interactive coordinators send requests. Unattended, isolated, offline, investigation and specialist request turns cannot send requests. Specialist execution cannot create Work, request input, change memory, manage agents or save artifacts directly. It returns proposed artifact text for the sender to save in the original conversation. Reply processing can send an explicitly chosen follow-up; incoming text itself grants no authority. There is no automatic recursive relay.

The recipient's normal private-context permission session is intersected with the initiating session and exact ancestor IDs/revisions. It never borrows an unrelated DM's authority. Changed/revoked permissions cancel applicable requests. Full access/Never does not fabricate reviews; confined modes remain enforced. Specialist approvals, MCP provider input and receipts are projected into the origin conversation, while authoritative private execution scope remains intact. Request provenance and receipts remain inspectable only through the scoped origin routes. Private execution rooms stay excluded from ordinary HTTP/WebSocket history.

## Completion, Work and restart

Execution and reply delivery are separate: accepted (Queued), running (Working), completed/incomplete/failed/cancelled/interrupted/legacy expired; reply delivery pending/delivered/failed. Successful delivered results disappear from current activity. Finished findings can be expanded while other requests work. A completed turn does not establish a business effect; action receipts remain authoritative. Cancellation cannot undo effects or clear Unknown.

Requests have no fixed five-minute deadline. Model/tool limits and the stalled-turn watchdog remain. Pausing the originating turn before dispatch cancels its unstarted admissions. Cancelling a queued request prevents execution; cancelling active execution or reply handling propagates its abort signal. Late output cannot replace a settled request or produce a second final delivery.

Messaging creates no Work. Requests from existing Work retain that source and cancellation ancestry. The source run can wait for replies without retaining the sender's admission or busy state; Work does not report completion before its replies settle. Reply turns retain Work/artifact attribution and legacy delegator return paths.

Admission keys deduplicate the same invocation; changed content under the same key is refused. A queued request becomes dispatchable only when its originating turn completes successfully. Orderly shutdown preserves dispatch-ready requests that have never started; recovery checks their original authority before first dispatch. Started execution becomes interrupted and is never automatically repeated. Started reply delivery is claimed before execution and is not replayed after restart. Known findings remain retained even if delivery fails. Unknown action receipts stay historical evidence and do not grant replay authority.
