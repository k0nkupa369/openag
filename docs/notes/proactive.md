# Composio-first proactive checking

Source behavior for the owner-approved searchable-picker V1. Deployment, live provider acceptance and physical notification receipt are separate checks.

## Configure

Open Settings, Proactive, Schedule. Services to check comes first, before scheduling. Search for a service through the existing Composio connection, select it and Save services. Only owner/Full access can search, save or read status (`GET /proactive`): status carries mailbox evidence (sender, subject, excerpt), so Limited devices get 403 and the desk shows them no selection or history. Search is an explicit metadata operation; opening settings and history reads local state only. Search results do not enumerate every connected service. Saving uses a revision; stale edits are refused instead of overwriting another device's selection.

A selected service includes all accounts that its current account listing returns, including accounts connected later. There is no account picker or two-account limit. Newly available services remain unselected. No services are selected on upgrade, and an empty selection performs no source checks: each due tick runs the model heartbeat instead (`createModelHeartbeat` in `heartbeat.ts`: one unattended, tool-limited turn in `_heartbeat` with the heartbeat prompt, only inside active hours, its verdict through the wake filter), so an install without services keeps a heartbeat. Enable Checking frequency separately. The default bot is used unless Checking frequency names one.

## Message destination

Settings → Proactive → Schedule, Message destination selects the default bot's chat or an existing room. Save destination uses the existing owner/Full-only deliveryRoom setting and reads it back. Existing main selections remain visible and unchanged until saved. The choice applies to morning briefs, proactive alerts and reflection proposals; queued briefs resolve it when delivered. Choosing the default bot stores no room ID and creates no chat until delivery. Unavailable saved rooms require an explicit replacement. Changing destination does not send a test message or alter alert/brief timing.

## Supported checks

| Service | Check | Scope |
| --- | --- | --- |
| Outlook | Recent incoming email | Inbox; IDs, subject, preview, received time and source link. |
| Gmail | Recent incoming email | Inbox; bounded message metadata/snippets, no payload or attachments. |
| GitHub | Recent notifications | Notification threads updated in the window; provider token type and notification scope must support this endpoint. |
| Other search results | No supported check yet | Retain explicit unavailable coverage and notify once per incident; do not guess a safe tool from its name or hints. |

The picker is not limited to these examples. Execution support depends on exact daemon-reviewed reads. The service/account choice is enforced before each tool call and again at connect/dispatch; it is not a prompt instruction. Explicit passive connection-list requests are read-only only when every item says `list`; missing/default actions cannot start authentication in background. All calls use the runner's normal permission gate and independent unattended ceiling. No second token manager or developer-project credential is added.

## Scheduling and coverage

Checks use Checking frequency. Notification hours affect wake delivery, not source inspection. Due times are stored in the daemon database and survive restart; a late scheduler admits one current opportunity, without replaying missed model turns. No overlapping scheduled checks are queued. Older attempts are prioritized so a deadline-limited cycle does not always start with the same service/account; deferred coverage remains explicitly Not checked. Enabling or changing service selection makes the next eligible scheduled tick due.

Each account has separate attempts, last successful read, covered window and page continuation. A first check looks back 24 hours. Its fixed window is saved before the first read, so cancellation or restart cannot drop the earliest unconfirmed range. Subsequent completed windows overlap by one minute and deduplicate source IDs/versions. A check reads at most two pages of ten items per account and has a five-minute overall deadline. More pages leave coverage Incomplete and retain the fixed window and continuation for a later check. Navigation markers are validated before storage and decoded only for the same reviewed request; unsupported or credential-bearing navigation leaves coverage Incomplete. A rejected/expired continuation restarts that same window without advancing its watermark; item deduplication survives the restart. Account inventories above the bounded 100-account response limit are explicitly incomplete rather than silently truncated. Read-only interrupted processing can inspect the retained range again; no historical model turn or action approval is replayed.

Reviewed Gmail/Outlook pages are projected by the daemon before the shared 20,000-character evidence cap. The projection retains every valid message ID, version/date, bounded sender, subject and excerpt, plus validated page navigation. It accepts Gmail messageId/messageTimestamp/messageText as well as preview fields (Gmail's `preview.body` first); a missing preview falls back to a bounded body excerpt. Gmail is read with `verbose: false` (metadata fetch: subject, sender, time and preview), because full message bodies made Composio replace the result with a sampled `data_preview` and a remote file. Such an offloaded reply is never read from its sample: the check records "The provider reply was too large to read inline" and keeps its window and page position. Full bodies, HTML payloads and attachment metadata are excluded, and structured evidence is not duplicated as text. Shortening an excerpt does not omit an item or page; successful coverage means these bounded records were processed, not that full message bodies were analyzed. Malformed identities, unsupported navigation, provider errors and truly oversized evidence remain incomplete without advancing coverage. The existing two-page budget, fixed window, item deduplication, atomic assessment/progress fence and saved continuation still apply across restart.

Excerpts are bounded and redacted. Assessment receives the current check's excerpts without earlier conversation history, bot memory, vector recall or assigned skills, and has no tools. ACP assessments start a fresh session per turn; ordinary ACP chat keeps session reuse. A valid assessment can stay quiet, produce a digest item or request an immediate ping through existing urgency, active-hours, duplicate and budget rules. Unsupported, malformed, oversized or failed responses do not establish successful coverage. A source read whose assessment fails or ends incomplete retains incomplete coverage, even if it emitted valid verdict JSON before stopping. Its items remain eligible for assessment on a later check. Model relevance remains a judgment, not proof that every important development was identified.

## Failures and recovery

In History, Service checks shows account coverage grouped by service in a responsive grid. A separate Recent checks table names each account and shows ten recorded checks per page, with Newer/Older controls. The arrow opens a read-only Check details sheet with the full reason, start/finish times, requested window and retained evidence. Closing it returns to the same history page. Review connection opens the existing Composio entry without changing access. Coverage shows the last successful read, plus up to fifty recent check records with outcome, inspected window and bounded evidence. No new items is distinct from no alert needed, incomplete, interrupted, cancelled or unavailable. Refresh reads retained state and does not run a check.

Provider account statuses are normalized for case and surrounding whitespace before checking eligibility; only ACTIVE accounts can dispatch reads. Unknown or inactive statuses do not gain access. An inactive account reports that its connection needs attention; an execution refusal/failure reports unavailable coverage without inventing a revoked grant or bad password. Account-list and content failures retain actionable sign-in, permission and rate-limit states. Other accounts continue. A previously checked account missing from the current listing remains visible as unavailable and is never replaced by another account. A known unavailable Composio connection or a transport outage observed across requests produces one grouped notice, even when the cached connection badge still says connected. Repeated observations reuse the same incident identity instead of sending new copies. Notification limits and quiet hours still apply, and held notices remain in retained wake/history state.

Recovery requires a successful supported read, not a connected badge or generic profile. Recovery information may enter the brief. Account inventory recovery is distinct from provider-content coverage. A missing configured bot settles the attempt with a setup reason. Execution limits report incomplete/deferred coverage and retain the last successful window. A service with no supported check never appears fully monitored.

Selection changes and pause prevent further scoped reads and publication. Paused checking also withholds queued proactive items from the brief; unrelated briefs are unchanged. Composio connection changes invalidate the prior selection revision for unpublished evidence. Unpublished digest items from an old selection revision are withheld from the brief. Raw proactive execution rooms are excluded from room APIs, turn inspection and the global event stream. Historical current-scope evidence is available in check history; after a selection revision changes, the retained outcome metadata remains but old excerpt content is withheld. Already delivered messages cannot be recalled.

## Limits and verification

This feature performs no provider writes, sends, drafts, attachment downloads, connection consent/reconnection, shell/workbench execution or implicit Work creation. It does not change ordinary interactive tool permission authority. Additional supported service checks need reviewed operations and coverage semantics; remote read hints are insufficient.

Standalone acceptance exercises public settings/search/history through the scheduler, real runner and HTTP MCP with synthetic provider accounts and captured notices. Mounted desk controls use the same disposable gateway. No unit/Jest/Vitest suite, actual mailbox/task read or live notification is required for controlled acceptance. Packaged help delivery is checked for API, Ollama, cached ACP/MCP and a replacement default bot. Rendered phone/desktop light/dark coverage must be recorded separately; a DOM check or build is not a visual pass.
