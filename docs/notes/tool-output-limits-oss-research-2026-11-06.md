# OSS tool-output limits — 6 November 2026

Research only. Current upstream source was checked on 6 November 2026 and pinned below; these are not claims about every installed version. No application code, settings, deployment or provider state was changed.

## Comparison

There is no common industry-wide character constant. All five projects bound model-visible output, but they count different units and expose different recovery paths. File preservation is especially common in terminal/interactive agents; it is not proof that every tool result can be safely truncated without changing its meaning.

Characters, UTF-8 bytes and tokens are not interchangeable. Python `len` counts Unicode code points; JavaScript string length counts UTF-16 code units; UTF-8 byte size varies with content. Token-based policies also need implementation-specific qualification: Deep Agents explicitly uses a character ratio. Comparing the numeric constants alone gives a misleading ranking.

## What this means for OpenAg

OpenAg's current `MCP_RESULT_CAP = 20000` limits the serialized wrapped evidence, including both textual and structured representations when present. It is therefore not a 20,000-character allowance for unique email text. Source: `apps/daemon/src/mcp/evidence.ts`, `remoteEvidence`. Its proactive Gmail request already asks for ten items with payload excluded, but the received verbose response can contain message text and metadata. The current proactive pre-cap transform preserves that body; `readPage` refuses a result marked truncated. Sources: `apps/daemon/src/proactive-composio.ts` and `apps/daemon/src/mcp/composio-contract.ts`.

**Recommendation (design inference, not an upstream requirement):** retain a generic safety ceiling, but make the proactive reader process a daemon-owned, validated page of bounded records before the generic model-output cap. Preserve every returned message ID, version/date, bounded subject/snippet and validated continuation token. Exclude full HTML/attachments and avoid serializing the same content twice merely to fit a model-facing wrapper. Assess small batches and commit progress only after successful assessment; never count an arbitrary clipped JSON preview as complete mailbox coverage.

If source-side field selection is supported by the reviewed Composio contract, request only the needed fields as well. If it is not supported, normalize and validate the returned source page locally. Smaller batches and bounded excerpts should handle a single large message without stalling the entire account, while clearly distinguishing excerpted content from a missing item/page.

OpenCode/Deep Agents/pi/OpenHands suggest a second useful pattern: retain overflow outside model context and expose bounded retrieval. OpenAg must adapt this to its permission model. A tool-free unattended assessment cannot use a returned file path to recover missing data. Do not silently enable filesystem or arbitrary retrieval tools for that assessment. If retained evidence is needed, keep it redacted, scoped and daemon-managed, with retention and access limits; otherwise prefer the smaller page projection first.

Raising 20k to 50k may postpone this incident but does not provide completeness or a durable large-mailbox strategy. The essential distinction is **bounded model input versus successful source coverage**, not the chosen integer.

## Limits of this research

Static source inspection and primary-source HTTP retrieval only. No upstream software was installed or executed, no unit/Jest/Vitest run, no benchmark or fresh provider read. Defaults can change after the pinned revisions.
