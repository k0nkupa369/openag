# Proactive features and automations

## Unread conversations and notifications

Unread badges identify direct chats and rooms with new visible agent messages, including questions, guest replies and proactive messages. A new-messages marker helps locate them and clears when they are read. After the first unread message comes into view, reaching latest in a visible conversation clears loaded unread messages across authorized devices, including Limited devices. If unread messages are outside loaded history, load earlier messages first. Reading does not answer a question or approve an action. A hidden tab or older history does not clear new messages.

When push (ntfy or Web Push) is enabled and configured, an unread completed reply, guest reply or open question can send a generic notification after five seconds. Reading it on any authorized device before that check suppresses the notice. Scheduled and proactive notices keep their existing filters and notification rules. Chat alerts share the hourly limit but leave one quarter, rounded up, for other alerts; at a limit of one, no chat alert can be sent. Unread remains when push is unavailable or capped. Push does not prove phone delivery; restart during the delay can lose the notice and does not replay it. See [conversation notifications](../notes/chat-notifications-domain.md).

Message destination in Schedule chooses where morning briefs and proactive alerts are posted: Default bot's chat or a room. Save destination applies the choice; the existing selection is kept until saved. Reflection proposals share this destination. Queued briefs use it when sent. Changing destination does not change notification hours or the brief schedule.

Settings, Proactive has Schedule, Reflection, Notifications and History tabs. Scroll within Schedule to reach the alert and morning-brief controls. Schedule starts with Services to check, followed by Message destination, Checking frequency, Proactive alerts and Morning brief. Search Composio for a service, select it and save. Search results are not a complete list of connected services. Selecting a service includes all its connected accounts, including accounts connected later; new services remain unselected. There is no account picker. With no service selected, each due check runs the model heartbeat instead (the heartbeat prompt within notification hours, through the wake filter). Upgrades do not select services automatically.

The daemon checks each account independently through reviewed reads. Large email replies are reduced to bounded sender/subject/excerpts while retaining message identities and pagination; Checked covers those excerpts, not full bodies or attachments. Incomplete checks retain their window and page position for later checks. Current checks cover Outlook Inbox email, Gmail Inbox email and GitHub notifications. Other services can be selected, but show No supported check yet and report unavailable coverage. GitHub notification access depends on its provider token type/scopes. Checking never sends mail, creates drafts, changes labels or accounts, reconnects, delegates or creates Work. The configured bot assesses bounded excerpts without tools; its custom heartbeat prompt can guide attention but cannot expand read scope. See the [proactive guide](../notes/proactive.md) for exact coverage, limits and recovery.

Checking frequency controls the schedule; notification hours filter alerts without stopping checks. Due times survive restart. History, Service checks separates successful reads, no new items, no alert needed, incomplete coverage and unavailable access. Accounts are grouped by service. Each recent check names its account and shows its outcome; expand it for the inspected window and evidence. Review connection opens the existing Composio entry. One account's failure does not stop another. A selected-account outage produces one notice per incident, subject to notification hours/limits; suppressed notices remain visible and may enter the brief. Recovery requires a successful supported read. Partial checks are not complete coverage. Pause or deselection prevents further scoped reads and withholds unpublished old-revision findings from the brief.

The existing wake filter chooses silence, digest or ping and applies repeat suppression, active hours, urgency and budget rules. Enabled checking does not mean every check sends a message. Morning brief assembles held digest items and pending approvals rather than starting a model turn. Reflection saves validated memory notes automatically; skill changes still require approval. Reflection Run now needs owner/Full access. The default bot is used when no explicit bot is selected.

openag_status reports whether heartbeat, reflection and the brief are enabled, not selected-service coverage, scheduler firing, provider acceptance or notification delivery; it never exposes push configuration or tokens. Use Settings, Proactive, History for checking evidence. openag_capabilities distinguishes disabled push, missing topic and configured service without probing, exposing the topic or sending a test. notify_user remains an external action requiring approval and is rate limited. Configuration and local delivery do not establish phone receipt.

Automations has schedules and supported external triggers. Cron is five-field with a minimum interval and overlap safeguards. Webhook-style events are verified before processing. GitHub polling uses outbound requests; Slack and webhook integrations have their own setup and restrictions. Triggered runs are unattended and generally isolated; they do not acquire action authority from event text.

The default bot can propose a scheduled room automation (create, change, turn on, pause or delete) with propose_automation. A proposal changes nothing: it is a card in that conversation showing name, schedule, time zone, bot, room, prompt and approval setting. Only the owner or a full-access device can accept it (applying exactly the card) or ignore it; it expires after 24 hours and is refused if the automation was edited since. Other bots, scheduled runs and hooks cannot propose; triggers, devices, permissions, connectors, MCP servers and secrets cannot be proposed. Never say a proposed change is done until the card was accepted.

Web Push sends the same short, end-to-end encrypted messages to the installed desk. The owner or a Full device turns on "Web Push for this OpenAg" in Settings → Proactive → Notifications with a mailto: or https: contact. On each device, Turn on for this device asks the browser for permission. It needs HTTPS (for example Tailscale Serve) or the same computer; iPhone and iPad need the Home Screen app. A click opens the approval or conversation. Removing a device stops its notifications; ntfy keeps working alongside it.

Automation history separates execution from scheduling diagnostics. Missed means supported scheduled opportunities passed without recorded admission; Skipped explains a known busy restriction; Start failed explains a setup/admission failure; Coverage gap means past coverage is uncertain. Diagnostics show scheduled/observed times and Not started, without a turn or Work. They do not send new alerts or imply that the task was investigated. See docs/notes/automations/README.md for the authoritative behavior and limits.

Cron tracking begins at upgrade or activation. Restart records overdue gaps without catch-up, and schedule edits never project into the past. Repeated recovery never sends another copy.

Standing responsibilities are separate from scheduled automations and explicit Work. In Automations, the Responsibilities tab lets the owner review exact sender/topic, permitted source resource, investigator, question and destination. Saving leaves it paused; enabling and edits require owner access and a current revision. Limited devices cannot change it. Editing pauses it for another review.

Automatic investigations use an approved source binding. The normal daemon has no live investigation source in this release: Outlook is unavailable, and synthetic acceptance does not connect an account. API/Ollama have the scoped investigation path; ACP investigations are unsupported and never fall back to unrestricted CLI tools. Ordinary ACP chat is unchanged.

Within that path, investigations can perform only curated approved reads. They receive no unrelated bot memory, vector recall, skills or conversation history. They cannot create Work, ask for action approval, delegate, send mail, create a provider draft or write memory. Proposed findings and replies are retained with source references and observation times. A suggested reply stays unsent. Missing access, records, stale evidence, execution limits and interruption do not certify business completion.

Pause, scope edits or source revocation block further reads and unpublished results. Interrupted investigations do not restart automatically. Findings open from a notice, morning brief or Investigation history. Raw investigation execution rooms are private; use those guarded views for inspection. The brief rechecks scope before showing queued result links. Stable event and result identities prevent duplicate attempts and local wake delivery; phone receipt remains unconfirmed. Previously delivered content cannot be recalled by pausing. See docs/notes/responsibilities.md for bounds and recovery details.
A failed reflection run can mean its model turn was interrupted, including by the watchdog. It does not mean a successful check found nothing to propose. See the [reflection guide](../notes/reflection.md).

Automations opens its Automations tab. New automation is in the page header; agent choices show avatars. Creation and saves show a toast, with counts below the list. Each row has an enabled switch and actions for Edit, History, Run now, webhook secret rotation and Delete. Delete and rotation require confirmation. Creating, editing, deleting and webhook secret rotation need the owner or a full-access device; limited devices can view automations, their history and use Run now. History shows recorded runs; Responsibilities has its own tab. See [Settings layout](../notes/settings-polish.md).

Scheduled automations show the effective time zone (inherited from the daemon unless set) and next run before saving; paused schedules have none, and invalid timing blocks saving. For Post in the room, choose an agent's direct conversation or a room and its current lead. The agent is saved; later lead changes do not change it. Existing assignments remain until the destination changes. Notify when needed uses the selected agent and notification filter; it may remain silent. See docs/notes/desk-part3c-ux.md.

Automations opens from Workspace navigation. History links open one automation or run without running it; an unknown ID shows not found. Proactive tabs restore through their address, and switching tabs preserves drafts.

Push also sends one minimal notice per new integration response request (shared hourly cap); answer it in the chat. Provider forms and links stay in the desk. See [provider input](../notes/mcp-lifecycle.md#needs-you-server-input).

To inspect a reflection, open Settings → Proactive → Reflection. Recent runs shows the last ten runs with status and recorded counts. Select a run's arrow to read its proposed memory notes and skill drafts, agent, time and duration. Full access is required for details. Refresh runs updates history without replacing unsaved schedule edits. Proposed content can include duplicate or over-limit notes; it does not certify that each note was saved. See the [reflection guide](../notes/reflection.md#inspecting-a-run) for historical counts and unavailable content. Opening details does not run reflection or approve a skill.

History separates Service checks coverage from Recent checks (ten per page, Newer/Older). A row's arrow opens Check details with reason, window, timing and evidence. Refresh reloads status without running a check. Services to check and history include mailbox excerpts, so Limited devices see neither. Held-back alerts show their reason and notification rule in plain text. Should have pinged still records feedback only; it does not resend an alert.
